T3c adds authenticated, backend-authorized interest additions and revision-checked contact corrections, without broad table mutation grants. Its disposable Auth scaffold proves concurrency, not real Auth integration. User consent allowed process-only script execution; no permanent policy changed.

T4a makes an inquiry a shared CRM entry with web, in-person or telephone origin. `create_manual_inquiry` self-assigns the active registering staff member, accepts an optional vehicle and optional email, reuses the normalized-phone advisory namespace and never overwrites a recognized contact. The observed RED was the missing `public.inquiry_origin` type; the focused suite then passed 67/67 and the complete suite after `pnpm db:reset`. The web submission still requires email and records `web` origin. An independent verifier reproduced the same RED, confirmed every T4a spec item and reported no blocker; its two advisories were corrected: non-staff identities are rejected before any inventory inspection, and stale planning notes were updated. Its probes are retained as `0010_manual_inquiry_verification_test.sql`, giving 374/374 for the complete suite. Manual creation has no client idempotency key yet, so a double submit can create two inquiries; UI submit protection and overlapping-session manual-creation coverage remain pending.

T4b adds inquiry-linked commercial reservations. `reserve_inquiry_vehicle` links one active inquiry, its contact and one Available, sale-enabled vehicle, records the creator and sets the vehicle Reserved atomically; partial unique indexes allow at most one active reservation per vehicle and per inquiry. `cancel_reservation` restores Available and retains history. Owner/Admin cancel any active reservation; a seller cancels only a reservation they created while the linked inquiry is still assigned to them. Triggers reject leaving Reserved, selling or soft-deleting a reserved vehicle, and reject reassigning, recontacting or closing without sale the inquiry that anchors an active reservation; reporting a sale stays allowed. The observed RED was the missing `sale_enabled` column and reservation types; the focused suite then passed 96/96 and the complete suite 470/470 after `pnpm db:reset`. `scripts/test-t4b-concurrency.ps1` retains seven overlapping-session scenarios: vehicle collision, inquiry collision, cancel-then-reserve, double cancel, reserve against a direct availability update, block-then-reserve and reserve-then-block. Equivalent probes were executed inline against isolated databases: every second session observed a lock wait, returned the exact expected SQLSTATE and message, and left stored rows unchanged, ending with one active reservation per vehicle and per inquiry, blocked inventory still unblocked in the winning reservation order and no deadlock. The runner itself was only syntax-checked in this session, because executing a `.ps1` needs separate authorization. Reservation creation still has no client idempotency key and no expiry or payment.

T4c adds internal sale blocking. `set_vehicle_sale_blocked` lets only an active Owner or Administrator block or re-enable sale eligibility; blocking is rejected while an active reservation exists, is separate from the reservation itself and leaves publication and availability untouched. The select policy now requires `sale_enabled` for the public branch, so a blocked vehicle leaves the anonymous catalog and direct public reads while active staff keep the full private inventory. The same guard trigger enforces the rejection for direct inventory updates, including the service role, so the existing generic vehicle update cannot bypass it. The observed RED was the missing function and a public catalog that still returned blocked rows; the focused suite then passed 58/58 and the complete suite 528/528 after `pnpm db:reset`. An Owner/Admin may still set availability to Reserved administratively: the approved baseline defines availability as an independent field and does not require every Reserved vehicle to hold a reservation, so no extra guard was inferred. Reservation creation still has no client idempotency key, no expiry and no payment.

On Windows, PowerShell resolves a `.ps1` shim before `.cmd`, so a disabled script-execution policy breaks `npm` but not pnpm when only the `.cmd` shim is installed. Use `pnpm.cmd` only as the fallback when a `.ps1` shim is present and blocked.

Do not add destructive cross-agency runtime tests before multiagency scope exists; schema design must still account for future evolution. Do not claim aggregate traffic proves causal conversion. Specify period/cohort rules and zero-denominator behavior before asserting metric expectations.

## Test-first and closure

For deterministic behavior with a runnable harness: observe a meaningful failing test, implement the change, then refactor while green. Test the public interface and persisted effects, not merely helper implementation details. Real backend permission tests cannot be replaced with mocks.

Each functional delivery must pass applicable formatting, lint, strict types, focused tests, relevant suites and build. Document exact commands and outcomes when tooling exists. Review mobile/desktop, keyboard access, empty/loading/error states and actual optimized image quality. No global coverage percentage is required.

For the current local shell, typecheck and build both workspaces and verify each loopback-only placeholder responds with HTTP 200. No deterministic business behavior or runnable business tests exist yet; RED/GREEN and backend permission proof remain pending. Never infer infrastructure readiness from shell builds.
